# إصلاح جذري لتعطل مولّد القصص

## الدليل المثبت
- نفّذت طلب تخطيط قصة حقيقي على الإنتاج بحساب العميل، وأعاد Backend Core الرمز `503 / AI_PROVIDER_TEMPORARILY_UNAVAILABLE` مع رقم تتبع.
- Lovable Cloud وقاعدة البيانات والمصادقة تعمل بصورة طبيعية.
- نقطة صحة الـVPS تعمل، وتؤكد أن مولّد النص المستخدم هو Gemini وأن خدمة Python معطلة؛ إذن الفشل في مسار NestJS → Gemini، وليس الصور أو PDF أو قاعدة البيانات.
- لا توجد مكالمات نص فاشلة في Lovable AI Gateway خلال نفس الفترة، لأن مولّد النص لا يستخدمه أصلًا.

## التعديل المقترح
1. إزالة تشغيل مرحلتي التخطيط والكتابة المتتاليتين داخل طلب إنشاء القصة نفسه؛ يحفظ Backend Core الطلب بحالة انتظار ويعيد هويته فورًا، ثم تكمل المهمة ويستمر الموقع في متابعة حالتها بالآلية الموجودة أصلًا.
2. وضع مهلة إجمالية واضحة لكل عملية Gemini تحت مهلة الموقع، بدل السماح لأربع محاولات × 30 ثانية؛ تبقى المحاولات داخلية ومحدودة ولا يُعاد إرسال طلب إنشاء القصة.
3. إبقاء 429 و5xx وانقطاع الشبكة فقط قابلة للمحاولة، ومنع المحاولة عند أخطاء المفتاح والصلاحيات والنموذج غير المدعوم ورفض المحتوى.
4. إضافة سجل آمن يوضح المرحلة وعدد المحاولات وحالة المزود ورقم التتبع، بلا prompts أو مفاتيح.
5. إضافة اختبارات: رجوع طلب الإنشاء سريعًا بحالة انتظار، نجاح المهمة وتحديث القصة، فشل المزود مع حفظ حالة قابلة للاستعادة، وعدم الخصم إلا بعد حفظ قصة ناجحة.

## التحقق
- تشغيل اختبارات مزود النص وموزّع المهام ومسار إنشاء القصة في Backend Core.
- تشغيل فحص TypeScript الخاص بالـBackend Core.
- إعادة اختبار طلب خطة حقيقي واحد بعد نشر نسخة الـVPS فقط؛ ثم اختبار قصة كاملة من الموقع المنشور إذا نجح التخطيط.

## قيد النشر
التعديل سيكون جاهزًا داخل مصدر Backend Core، لكن نشره على `najmah-api.nextnext-gen.com` يحتاج قناة نشر الـVPS الحالية. لن أغيّر Lovable Cloud أو قاعدة البيانات أو الصور أو PDF.
